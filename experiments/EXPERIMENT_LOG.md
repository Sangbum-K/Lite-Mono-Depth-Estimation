# 전체 실험 기록 (Lite-Mono 재현 → 한계 분석 → 개선 가설 검증)

실험마다 **왜 했는지 / 하기 전 가설·예상 / 방법 / 결과 / 확인한 것 / 한계**를 기록한다.
수치는 모두 KITTI Eigen test 697장, 같은 평가 코드(median scaling, 80m cap, Garg crop, post-process 없음) 기준이다.
코드·환경이 논문과 다른 점은 `CHANGES.md`, baseline 학습의 세부 설정은 `experiments/20261109_baseline_unseeded.md`에 있다.

- 경계 지표 용어 (E5에서 정의, 이후 모든 실험에서 같은 경계 3,263개 사용)
  - **4px 이내**: 예측 경계가 LiDAR 경계에서 ±4 GT px 안
  - **번짐**: 예측 경계가 배경 쪽으로 4px 넘게 밀림 (물체가 부풀어 보임)
  - **물체 놓침**: 물체 안쪽 15px에서 이미 배경 깊이 (물체가 배경에 먹힘)
- px는 따로 표시하지 않으면 KITTI 원본(GT) 픽셀. 모델 해상도(640×192) 1px ≈ 원본 약 2px.

## E0. 공개 checkpoint 평가 (2026-11-09)

- **왜**: 학습 전에 평가 코드·데이터·GT 생성이 논문과 같은지 확인. 로컬은 PNG 원본을 쓰므로(논문은 JPG) 입력 포맷 차이도 확인.
- **가설·예상**: 평가 파이프라인이 맞다면 공개 checkpoint가 논문 Table 1 수치를 내야 한다. PNG/JPG 차이는 작을 것.
- **방법**: `pretrained/kitti_640x192`를 학습 없이 `scripts/eval_eigen.sh`로 평가. 이 과정에서 `evaluate_depth.py`가 `--png`를 무시하는 upstream 버그를 찾아 수정(CHANGES 4.1b).
- **결과**: AbsRel 0.107 / SqRel 0.766 / RMSE 4.560 / RMSElog 0.183 / δ1 0.886 (논문 0.107 / 0.765 / 4.561 / 0.183 / 0.886).
- **확인한 것**: 평가 파이프라인이 논문과 같다. JPG로 학습된 모델을 PNG로 평가해도 수치가 같다.
- **산출물**: `outputs/public_kitti_640x192_eval/eval_png.log`

## E1. Baseline 재현 학습 (2026-11-09, `20261109_baseline_unseeded`)

- **왜**: 개선 실험의 기준이 될 모델을 같은 환경에서 직접 학습해야 비교가 공정하다.
- **가설·예상**: 공식 코드·하이퍼파라미터(batch 12, 30 epoch, lr 1e-4→5e-6, cosine 31 epoch 주기)로 학습하면 논문 수치에 근접한다.
- **방법**: RTX 5070, PNG 입력, seed 없음, num_workers 6. 약 9시간.
- **결과**: `weights_29` AbsRel 0.107 / SqRel 0.821 / RMSE 4.608 / RMSElog 0.184 / δ1 0.887. 3.069M params, 5.032 GMACs.
- **확인한 것**: AbsRel·RMSElog·δ는 논문과 ±0.001 안이므로 재현 성공. SqRel만 +7%(0.821 vs 0.765).
- **한계**: SqRel 차이가 PNG 입력 때문인지 run 편차 때문인지 모른다. epoch 19–29 사이에도 SqRel이 0.795–0.867로 흔들렸다.
- **산출물**: `experiments/20261109_baseline_unseeded.md`(epoch별 표 포함), `outputs/20261109_baseline_unseeded/`

## E2. 실패 분석 (2026-11-23)

- **왜**: 개선 방향을 정하려면 오차가 어디에 몰려 있는지 알아야 한다.
- **가설·예상**: 별도 가설 없이 탐색. 후보 요인은 소수 이미지 집중, 먼 거리, 깊이 경계, 영상 밝기 경계.
- **방법**: `analysis/baseline_failure_analysis.py`로 이미지별·거리별·영역별 오차와 Spearman 상관, 고정 규칙 샘플 그림(worst 20, best 5, random 10)을 만들었다. 평균을 재계산하면 `evaluate_depth.py`와 일치한다.
- **결과**
  - 이미지별: 오차 최악 10%가 오차 합의 17.9%. 소수 이미지가 평균을 끌어올리는 구조가 아니다.
  - **깊이 경계 근처(9×9 안에서 깊이 1.25배 이상 차이)**: LiDAR 점의 11.5%인데 AbsRel 합의 28.1%. AbsRel 0.260 vs 나머지 0.086. 이미지별 AbsRel과의 상관이 +0.54로 조사한 요인 중 가장 강했다.
  - 거리: 0–20m 0.088 / 20–40m 0.155 / 40–80m 0.201. 40m 이상은 너무 가깝게 예측하지만 점의 5.7%뿐이다.
  - 경계 양쪽 분리: 배경 쪽은 29% 가깝게, 물체 쪽은 18% 멀게 예측. 깊이가 경계를 넘어 섞이는 **번짐(edge fattening)**이다.
- **확인한 것**: 개선 대상은 깊이 경계, 그중에서도 번짐이다.
- **산출물**: `outputs/20261109_baseline_unseeded/analysis/weights_29/summary.md`, `figs/`

## E3. 오차 상위 30% 이미지 검사 (2026-11-23)

- **왜**: 최악 이미지가 특별히 경계 때문에 나쁜 것인지, 경계 번짐이 모든 이미지의 공통 문제인지 구분하기 위해.
- **가설·예상**: 최악 이미지일수록 경계 오차 비중이 클 것이다.
- **방법**: `analysis/inspect_worst_fraction.py`로 상위 30%(209장)와 나머지를 영역별로 비교하고, 209장을 직접 확인했다.
- **결과**: 상위 30%는 경계(0.329 vs 0.221)뿐 아니라 평탄 영역(0.129 vs 0.070)과 0–20m(0.139 vs 0.067)도 나쁘다. 오차 중 경계 비중은 비슷하다(29.9% vs 26.8%).
- **확인한 것**: 예상과 달랐다. 경계 번짐은 **모든 이미지의 공통 약점**이고, 최악 이미지는 장면 전체의 구조 오류가 겹친 경우다. 직접 본 유형: 주차 차량 윤곽, 트럭·정체 장면, 트인 도로의 먼 수풀, 철망·덤불.
- **산출물**: `.../weights_29/worst30/`

## E4. 투과 점 분리 (2026-11-27)

- **왜**: LiDAR가 유리·철망을 통과해 뒤쪽을 측정하면 GT 자체가 틀린다. 경계 오차 중 이런 GT 문제의 비중을 알아야 한다.
- **가설·예상**: 경계 오차의 상당 부분이 투과 점일 수 있다.
- **방법**: 경계 배경 쪽 점 중 같은 행 좌우 20px 안에 더 가까운 점이 모두 있는 점(사방이 둘러싸인 점)을 투과 점으로 분리했다.
- **결과**: 투과 점은 오차의 1.2%뿐이다. 윤곽 바깥 배경 쪽이 12.3%(AbsRel 0.288, 평균 약 29% 가깝게)다.
- **확인한 것**: 예상과 달리 GT 문제는 작고, **물체 윤곽 바깥 배경이 핵심**이다. 단, 차 유리창은 20px보다 넓어 이 판정을 일부 빠져나간다.

## E5. 픽셀 단위 경계 위치 측정 (2026-11-27)

- **왜**: 영역 평균 AbsRel로는 경계가 몇 px, 어느 방향으로 밀렸는지 알 수 없다. 개선 효과를 판단할 직접 지표가 필요했다(본인 설계).
- **방법**: `analysis/edge_offset.py`. LiDAR 행에서 깊이가 1.25배 넘게 뛰는 인접 점 쌍 중 양쪽이 일관된 면인 경계 3,263개(645장)를 골랐다. 예측 log depth가 물체·배경 깊이의 중간값을 처음 넘는 위치를 예측 경계로 보고 실제 경계와의 거리를 쟀다.
- **결과 (baseline ep30)**: 4px 이내 25.4% / 번짐 27.7% / 물체 쪽 밀림 7.1% / 물체 놓침 22.9% / 배경 미도달 16.9%. 측정된 경계의 중앙값은 +3.5px.
- **확인한 것**: 번짐(배경 쪽)이 물체 쪽 밀림의 약 4배로 **한쪽으로 치우친 오차**다. 이 비대칭은 이후 가설 판단의 근거가 됐다(E7).
- **산출물**: `.../weights_29/edges/summary.md`, `edges.csv`. 그림은 `boundary_overlay/`, `boundary_zoom/`

## E6. Depth Pro 2 비교 (2026-11-27)

- **왜**: 경계 오차 중 **모델이 줄일 수 있는 부분**과 **GT 문제**를 구분하기 위해. 경계가 선명하도록 설계된 강한 모델도 틀리는 오차는 GT 문제로 본다.
- **가설·예상**: 번짐이 모델 한계라면 Depth Pro 2에서 크게 줄고, GT 문제라면 비슷하게 남는다.
- **방법**: Depth Pro 2-S(24.3M), H+(872M) 공개 가중치를 원본 해상도로 추론하고(`analysis/run_depth_pro_2.py`, 분리 환경), 같은 평가·경계 코드로 비교했다(`compare_models.py`).
- **결과**

  | 항목 | Lite-Mono | DP2-S | DP2-H+ |
  |---|---|---|---|
  | AbsRel | 0.107 | 0.108 | 0.074 |
  | 4px 이내 | 25.4% | 42.1% | 51.1% |
  | 번짐 | 27.7% | 15.0% | 14.1% |
  | 물체 놓침 | 22.9% | 22.5% | 19.5% |
  | 투과 점 AbsRel | 0.357 | 0.359 | 0.355 |

- **확인한 것**
  - DP2-S는 전체 AbsRel이 같은데 번짐이 절반이다. 그러므로 **번짐은 줄일 수 있는 오차**다.
  - H+는 S보다 36배 크지만 번짐이 거의 같다. 번짐은 모델 크기로 줄어드는 오차가 아니다.
  - 물체 놓침과 투과 점 오차는 세 모델이 같다. **GT 문제로 보고 개선 대상에서 제외**했다.
  - Lite-Mono에서만 나쁜 25장 중 오차가 큰 8장(`sheet_only_lm_h.png`)은 트인 도로의 먼 수풀을 멀게 예측한 장면 2장, 나무·그림자가 많은 좁은 길 5장, 정체 차량 장면 1장이었다. 오차가 장면 넓은 영역에 퍼져 있어 장면 배치 문제로 보고 범위에서 제외했다. (11-28 점검: 처음에는 "대부분 트인 도로의 먼 수풀"로 적었으나 그림과 맞지 않아 고침)
- **정정한 해석**: 처음에는 리포트에 "구조가 중요하다"고 썼다. 그러나 DP2는 구조와 **깊이 정답 지도학습**이 함께 다르므로, 이 비교로는 원인이 구조인지 손실인지 나눌 수 없다고 고쳐 썼다. 이 질문이 E7–E12로 이어졌다.
- **산출물**: `outputs/depth_pro_2/compare/compare.md`, `research/depth_pro_2_notes.md`

## E7. 원인 후보 점검과 후보 설계 (2026-11-27)

- **왜**: 번짐의 원인 가설을 세우고, 가설마다 그 부분만 바꾸는 후보를 같은 조건에서 비교하기 위해(실험 설계는 본인 설계).
- **점검한 내용**
  - **decoder 구조**: encoder의 1/2 해상도 stem feature(48채널)가 decoder에 전달되지 않아, 가장 세밀한 skip이 1/4 해상도(원본 약 8px)다. 최종 출력은 1/2 해상도에서 bilinear로 키운다.
  - **smoothness 가중치**: 학습 영상 150장의 밝기 기울기 분위수는 p50 0.013, p95 0.130, p99 0.276이다. 원래 가중치 exp(−g)는 p95 경계에서도 0.88이라 **밝기 경계에서 smoothness가 거의 풀리지 않는다**.
    - 11-28: 이 측정은 스크립트가 남아 있지 않은 일회성 측정이다. 리포트에서는 수치를 빼고 코드의 식만 쓴다(가중치 exp(−|∂I|), |∂I|는 0–1이므로 0.37 이상). 다시 측정하려고 만든 스크립트도 임의로 만든 것이라 제거했다.
  - **연산량 목표**: 자율주행용 경량 모델이므로 추가 연산 약 3% 이내로 정했다. 1024×320 입력은 약 2.7배라 제외했다.
  - **선행 연구**: HR-Depth(구조 원인, 14.6M), SuperDepth(sub-pixel), Chen 등 WACV 2023(가려짐 원인, 분할 기반 triplet loss), BoRe-Depth(경량 모델 경계 개선, 여러 변경을 함께 적용).
- **세운 가설**
  - **가설 1 (decoder 구조)**: 해상도 부족과 bilinear 보간 때문에 경계가 밀린다.
    - 예측: 1/2 해상도 skip과 학습형 upsampling을 넣으면 4px 이내 비율이 오르고 번짐이 준다.
  - **가설 2 (자기지도 손실)**: 가려진 배경에서 photometric loss가 물체 깊이를 선호하고, smoothness가 경계를 덮는다.
    - 예측: 구조를 바꿔도 번짐은 그대로이고, 손실을 바꿔야 준다.
  - 근거 점검: 번짐이 한쪽으로 치우친 것(E5)은 대칭인 bilinear로 설명되지 않으므로 가설 2 쪽이다. 4px 이내가 25%뿐인 것은 가설 1과도 맞다. 그래서 둘 다 시험하기로 했다.
- **후보** (thop 640×192)

  | 후보 | 가설 | 변경 | 연산량 |
  |---|---|---|---|
  | A | 1 | stem 48ch skip + transposed conv | +10.3% (5.550G) |
  | A-lite | 1 | stem을 1×1 conv로 8ch 압축 + sub-pixel head | +1.7% (5.117G) |
  | B | 2 (smoothness) | smoothness 가중치 1e-3 → 1e-4 | 0 |

  | D | 2 (가려짐) | Chen 등 triplet loss (비교 기준) | 0 (미구현) |

  - A-lite는 처음에 skip만 압축하면 +5.3%라 목표를 넘어, sub-pixel head를 더해 +1.7%로 맞췄다.
  - C의 계수 10은 위 분포만 보고 정했고 test 결과로 조정하지 않았다.
  - 모든 옵션은 기본값이면 원본과 같다: A는 공개 checkpoint 출력이 동일했고, C는 gain 1.0에서 비트 단위로 같았다.

## E12. 손실 함수 진단, V2 (2026-11-28)

- **왜**: E8과 E10으로 가설 1은 약해졌고 smoothness 후보도 효과가 없었다. 남은 가설 2의 핵심(photometric 신호)을 **학습 없이 직접** 확인하고 싶었다. Chen 등은 가려짐 원인을 그림으로 설명했지만, 우리 데이터에서 실제로 측정한 결과는 없었다(진단 방법은 본인 설계).
- **가설·예상**
  - 가설 2가 맞다면, 경계 바로 옆 배경 픽셀에서는 photometric loss가 정답(배경) 깊이보다 물체 깊이에 더 작은 값을 준다. 경계에서 멀어지면 이 선호는 사라진다.
  - 그 선호가 있는 경계에서 학습된 모델이 더 많이 번진다.
  - 가려짐이 원인이라면 다른 프레임에서는 배경이 보이므로, 원본 프레임을 ±2로 늘리면 선호가 줄 것이다.
- **방법**: `analysis/loss_preference.py`
  - baseline ep30의 depth·pose network를 쓰고, 테스트 영상의 앞뒤 프레임을 읽었다.
  - 손실은 학습과 같게 계산했다: 640×192 Lanczos, 0.85×SSIM(3×3) + 0.15×L1, 원본 프레임 중 최솟값, identity loss.
  - E5의 경계마다 같은 행에서 물체 안쪽 6px부터 배경 16px까지(모델 해상도 px) 각 픽셀에 물체 깊이와 배경 깊이를 주고 손실을 비교했다. 3×3 패치는 같은 깊이로 warp했다.
  - 깊이는 같은 영상의 median scaling 비율로 모델 scale로 바꿨다.
  - 두 깊이의 warp 위치 차이가 0.5px 미만인 픽셀(정지 차량 등)은 제외했다. 앞뒤 프레임이 없는 경계 102개도 제외했다.

  - **가설 2와 맞음(상관관계)**: 손실의 치우침과 번짐이 같은 경계에서 함께 나타난다. 손실이 원인임을 증명하지는 않는다(두 가지 모두에 불리한 경계가 함께 작용했을 수 있다).
  - **가설 1 약화**: E8의 A 계열 결과, E10의 "학습해도 안 줄어드는 번짐"과 일관된다.
- **한계**
  - 원인이 가려짐인지 경계 픽셀의 색 혼합인지는 구분하지 못했다. ±2 프레임에서 변화가 없는 것은 단순한 가려짐보다 혼합 쪽일 가능성도 시사하지만 단정할 수 없다.
  - pose는 학습된 pose net의 추정값이다.
  - 배경 1–2px은 3×3 SSIM 패치가 경계에 걸친다.
  - 물체 안쪽에서도 정답을 68%만 고르므로, 손실은 픽셀 단위로는 잡음이 큰 기준이다.
  - 분석한 모델은 ep30 하나다.
- **산출물**: `outputs/20261109_baseline_unseeded/analysis/weights_29/loss_preference.md`, `loss_preference.csv`

## E14. 후보 E: Depth Pro 2 decoder 구조 (2026-11-28, 구현과 비용 측정만)

- **왜**: 사용자 지적. A, A-lite는 decoder 마지막 단계만 바꾼 작은 변경(파라미터 +0.09–0.39%)을 5 epoch 한 번씩 본 것이라, "구조는 원인이 아니다"라고 하기에는 근거가 약하다. 경계가 선명한 Depth Pro 2의 구조를 참고하자는 방향도 사용자 제안이다.
- **Depth Pro 2 코드에서 확인한 것** (`third_party/ml-depth-pro-2/src/depth_pro_2/network/`)
  - encoder는 DINOv3 ViT(패치 16)다. 4단계 피라미드는 모두 1/16 토큰을 학습형 확대(transposed conv)로 1/4, 1/8로 키워 만든다. 따라서 가장 세밀한 encoder 정보는 16px 패치 단위로, KITTI 원본(1242 → 1248) 폭 기준 78칸이다. Lite-Mono의 1/4 feature(640 기준 160칸)보다 거칠다.
  - decoder(DPT)는 단계마다 `x + resnet1(skip)` → `resnet2` → ConvTranspose 2× → 1×1 conv로 진행한다. head는 3×3 conv → ConvTranspose 2× → 3×3 conv(32) → ReLU → 1×1 conv다. Lite-Mono는 모든 단계에서 bilinear로 키운다.
  - 해석: 경계 선명도는 고해상도 skip보다 학습형 확대·정제 방식 또는 학습 방법(정답 지도학습)에서 올 가능성이 있다. A의 방향(고해상도 skip 추가)은 Depth Pro 2가 하는 방식이 아니었다.
- **구현**: `DPTDepthDecoder` (`--dpt_decoder --dpt_dim N --dpt_head_ch M`). encoder는 그대로 두었다. Lite-Mono와 맞추려고 출력은 sigmoid disparity를 쓰고, 다단계 출력(scale 2는 1/4, scale 1은 1/2, scale 0은 head 출력인 원해상도)을 유지했다.
- **비용** (`analysis/model_cost.py` → `outputs/model_cost.md`, thop, 640×192): A와 A-lite 값은 기존 기록과 같다.

  | 변형 | 연산량 | 파라미터 |
  |---|---|---|
  | Baseline | 5.032G | 3,074,747 |
  | A / A-lite | +10.3% / +1.7% | +0.39% / +0.09% |
  | DPT dim 64 (Depth Pro 2-S 채널) | +81.9% | +12.51% |
  | DPT dim 32, head 16 | +11.6% | −1.18% |
  | **DPT dim 24, head 16** | **+2.0%** | **−3.42%** |
  | DPT dim 16, head 16 | −5.5% | −5.20% |

  - 원래 decoder는 0.718G다. 파라미터가 줄어드는 것은 원래 decoder의 1/16 단계 conv(128→64 등)보다 DPT의 채널이 작기 때문이다.
- **동작 확인**: 실제 학습 배치 1개(batch 12)로 학습 손실 계산과 역전파를 했다. 저장이나 optimizer step은 하지 않았다. 손실 0.171, GPU 최대 7.6GB, decoder 파라미터 44개 모두에 gradient가 생겼다. state_dict를 평가용 생성자로 다시 불러오는 것도 확인했다.
- **추론 시간** (11-28 추가, 사용자 지적: 자율주행에는 연산량보다 실제 추론 시간이 중요하고, baseline Lite-Mono와 비슷한지가 기준). `analysis/model_cost.py`로 쟀다. 조건은 FP32 PyTorch이고, 시간은 가중치 값과 상관없다.
  - **논문 기록** (arXiv 2211.13202 4.5절 Table 4, 공식 README 속도 그래프): 640×192, 이미지당 시간. 하드웨어는 NVIDIA TITAN Xp(데스크톱)와 Jetson Xavier(차량·로봇용 임베디드 보드)다.

    | | TITAN Xp, batch 1 | TITAN Xp, batch 16 (Table 4) | Jetson Xavier, batch 1 | Jetson Xavier, batch 16 (Table 4) |
    |---|---|---|---|---|
    | Monodepth2 | 7.1 | 3.8 | 18.6 | 14.3 |
    | Lite-Mono | 9.1 | 4.5 | 24.6 | 20.0 |
    | Lite-Mono-8M (연산량 2.2배) | 9.6 | 6.5 | 36.0 | 32.2 |

  - **로컬 측정** (RTX 5070 GPU, Ryzen 7800X3D CPU 4 thread; GPU는 500회, CPU는 50회의 중앙값; 이미지당 ms; 세 번째 실행, `outputs/model_cost.md`). GPU는 실행 간 0.1ms 이내로 재현됐고, CPU는 ±5%p 정도 흔들렸다.

    | 변형 | 연산량 | GPU batch 1 | GPU batch 16 | CPU batch 1 |
    |---|---|---|---|---|
    | Baseline | 5.03G | 3.59 | 2.02 | 51.5 |
    | A | +10.3% | +4% | +14% | −1% |
    | A-lite | +1.7% | +1% | +2% | −9% |

    | E dim 32 | +11.6% | +7% | +12% | +7% |
    | E dim 24 | +2.0% | +6% | +8% | +3% |
    | E dim 16 | −5.5% | +3% | +2% | −13% |

    - 로컬 baseline은 논문 TITAN Xp보다 batch 1에서 약 2.5배, batch 16에서 약 2.2배 빠르다. batch 1이 batch 16보다 이미지당 느린 경향은 논문과 같다.
    - GPU가 덜 바쁜 batch 1에서는 연산량 차이가 시간에 덜 반영된다(dim 64: +17%). GPU가 바쁜 batch 16과 약한 CPU에서는 연산량이 더 반영된다(+41%, +45%). Jetson이 없으므로 CPU를 약한 기기의 대용으로 쓴다(가정).
    - 절대 시간: GPU에서는 모두 약 4ms 이하라 30 FPS(33ms)를 충분히 만족한다. CPU에서는 baseline도 약 52ms라 30 FPS를 못 맞추고, 10Hz(100ms)는 모두 만족한다.
- **다음**: 5 epoch 예비 학습(`--dpt_decoder --dpt_dim 24 --dpt_head_ch 16`)은 사용자 지시가 있을 때 한다. 채택 기준은 사용자 결정으로 "baseline 대비 추론 시간 증가 10% 이내(GPU 1장씩, GPU 16장씩, CPU 1장씩 모두)"로 바꿨다. 이 기준이면 A(16장씩 +14%)는 탈락하고 A-lite, E dim 24는 통과한다. E dim 24의 5 epoch pilot은 11-28 15:12에 시작했다(`run_pilots.sh E` → `outputs/20261128_dpt24_e5`, ep4·ep5 평가·분석 포함).
- **5 epoch pilot 결과** (15:12–16:22, 평가·분석 포함; `outputs/pilots_summary.md`, `outputs/pilots_ad.md`, `analysis/weights_3·4/edges/summary.md`). 비교 기준은 두 baseline 학습의 ep4·ep5 범위다(AbsRel 0.117–0.122, 4px 이내 19.3–21.7%, 번짐 25.1–28.7%, 물체 놓침 25.9–29.8%).

  - **가설 판정**: decoder 전체를 Depth Pro 2 구조로 바꾸어도 A·A-lite와 같은 방향이었다(물체 놓침은 줄고 번짐은 늘며, 4px 이내 비율은 오르지 않음). 5 epoch, 학습 1회 기준으로 가설 1(decoder 구조)은 지지되지 않는다. 학습 신호가 핵심이라는 해석(E12)과 맞는다.
  - **한계**: 학습 1회이고 5 epoch다. encoder와 입력 해상도는 바꾸지 않았다. 물체 놓침 감소는 baseline도 학습 후반(ep10 이후 22.4–23.4%)에 도달하는 수준이다.

## 해석을 고친 기록

1. **E6**: "구조가 중요하다" → DP2는 지도학습이라 구조와 손실을 나눌 수 없다고 수정(11-27).
2. **E8, E9**: "B, A-lite, A가 가까운 거리에서 좋아졌다" → 인접 epoch 차이(E10)가 더 커서 효과로 볼 수 없다고 수정(11-28).
3. **E8**: "ep4와 ep5 모두에서 A와 A-lite가 같은 방향이다" → A는 ep5에서 baseline과 1%p 이내라 **A-lite만** 일관된다고 수정(11-28).
4. **11-28 숫자 전수 점검** (리포트 숫자를 원본 출력과 대조): 표의 숫자는 모두 원본과 일치했고, 다음 서술을 고쳤다.
   - E8·E11: "A-lite뿐" → A의 물체 놓침도 두 시점 모두 범위 밖(22.8%, 25.3%).
   - E12: "1.5배, 11%p, 5.8 표준오차" → 원본 CSV로 다시 계산해 1.4배, 10.3%p, 5.5 표준오차. "고대비에서 연결이 더 강하다" → 하위와 상위 차이 1.5 표준오차라 구분 불가. "경계 약 8px 안에서 구분 못함" → 구분 못하는 곳(50%)은 바로 옆 1–2px, 그 바깥은 치우침. 상관관계임을 명시.

## 다음 단계 (리포트 6.7절과 같음)

- 경계에 photometric loss가 아닌 신호를 준다. 1순위는 후보 D(분할 기반 triplet loss)이고, E12에서 손실이 모호했던 경계 주변 약 4 모델 px에만 적용하는 형태도 시험한다.
- 큰 깊이 모델의 pseudo-label(BoRe-Depth 방식)은 학습 사용이 허용된 모델로 한정한다. Depth Pro 2는 연구용 공개라 학습에 쓰지 않는다. 11-28에 DP2 경계 손실 실험을 제안했지만 사용자 결정으로 하지 않았다.
- 구조 쪽은 decoder 전체를 Depth Pro 2 구조로 바꾼 후보 E(E14)로 다시 확인한다.
- 비교는 여러 checkpoint 평균과 두 번 이상의 학습으로 한다. 후보 평가에 E12의 진단도 함께 쓴다.
- 30 epoch 전체 학습은 최종 보고서에서 한다.

## 부록: 실행 환경 이슈 (결과에는 영향 없음, 재현할 때 참고)

- **RAM 15GB 제약**
  - 학습 하나가 약 7GB를 쓴다(미리 읽어 둔 batch의 공유 메모리 4.2GB 포함).
  - 학습 두 개가 겹쳐 OOM이 났다(11-27 18:13). 이후 `run_pilots.sh`에 중복 실행 잠금, OOM 재시도·중단 로직을 넣었다.
  - 검증 loader worker를 1개로 줄였다(`--val_num_workers`).
- **GPU 대기**
  - 데이터 준비(PNG 디코딩 + 4단계 Lanczos resize)가 CPU 병목이었다. GPU는 약 58장/s를 처리할 수 있었지만 실제로는 26장/s였다.
  - worker를 4개에서 6개로 늘리고 OMP 스레드를 1로 맞추자 실험당 2시간 5분에서 68분으로 줄었다.
  - 학습 계산 자체는 같다.
- **스케줄**: 모든 5 epoch 실험은 baseline과 같은 31 epoch cosine LR 주기를 쓴다.
